# 과제 8 인증 구현 설명서 — 실제 기기 확인 전 준비본

확인일: 2026년 10월 6일 (Asia/Seoul)

공개 소개는 T01 ‘솜사탕의 작은 이야기’를 이어받았다. 비공개 메모는 별도 서버 자료이며, 모두 만들어 넣은 가상 내용이다. 실제 연락처, 신분증, 비밀번호, 개인키는 사용하지 않는다. 아직 실제 기기 확인이 끝나지 않았으므로 이 문서는 최종 제출본이 아니다.

## ① 무엇으로 붙였나

라이브러리 방식: `@simplewebauthn/server 14.0.3`과 `@simplewebauthn/browser 14.0.0`을 사용한다. 서버의 서명·origin·RP ID·사용자 확인 검증은 SimpleWebAuthn이 담당한다. 계정, 세션, challenge의 수명·일회 사용, 메모 접근 권한은 앱이 구현했다. D1에 계정·공개키·세션 해시·일회 질문·가상 메모를 저장한다.

사이트에는 비밀번호 입력칸이 없다. Windows Hello가 기기 PIN을 요청하는 것은 운영체제가 패스키 사용자를 확인하는 절차이며 사이트의 비밀번호가 아니다.

서버에 저장되는 `public_key`는 COSE 공개키를 base64url로 표현한 값이다. `TEST_PUBLIC_KEYS.json`은 자동 검증에서 실제로 저장된 공개키 값이다. 이 키들은 Node에서 생성한 합성 인증기의 키이므로 실제 기기 등록 증거로 사용하지 않는다. 등록 요청 본문은 공개 credential ID, clientDataJSON, attestationObject와 transports를 포함하고 개인키를 포함하지 않는다. 개인키는 실제 사용 시 선택한 패스키 제공자가 보관한다. 동기화형 패스키는 제공자의 암호화된 동기화를 이용할 수 있으며, 앱 서버에 개인키를 보내지 않는다.

## ② 왜 그걸 골랐나

등록 질문 발급 → 응답 검증, 로그인 질문 발급 → 공개키로 서명 검증 흐름을 분명히 보여 줄 수 있다. 암호·CBOR·서명 알고리즘을 앱에서 직접 작성하는 대신 라이브러리가 검증하고, 앱은 계정별 자료 보호와 과제의 일회 사용 요구를 담당한다.

공식 문서: https://simplewebauthn.dev/docs/packages/server 및 https://simplewebauthn.dev/docs/packages/browser

## ③ 어디를 어떻게 고쳤나

| 흐름 | 소스 위치 | 동작 |
| --- | --- | --- |
| 공개 소개 | `app/page.tsx`, `app/globals.css` | T01의 소개·관심사·경험·프로젝트를 보존하고 메모함 입구 추가 |
| 등록 화면 | `components/private-room.tsx`의 `register` | 별명·키 이름·직접 선택한 저장 위치를 받고 브라우저의 패스키 등록 창 시작 |
| 등록 서버 | `app/api/passkey/[...path]/route.ts` → `lib/passkey.ts`의 `optionsRegistration`, `verifyRegistration` | 임시 질문 저장, 라이브러리 검증 후 공개키 저장. 가입은 성공한 뒤에만 계정·가상 메모 생성. 추가 등록은 로그인한 본인 계정만 허용 |
| 로그인 | 같은 route → `optionsLogin`, `verifyLogin` | 새 질문 발급, 저장 공개키로 서명 검증, 통과한 credential의 계정으로 세션 발급 |
| 로그아웃 | `handle`의 `logout` 분기 | 서버 세션 삭제, 쿠키 만료, 대기 질문 무효화 |
| 자료 조회 | `app/api/private/notes/route.ts`, `app/api/private/notes/[id]/route.ts` → `privateData` | 세션 없으면 401. 개별 메모의 소유자가 다르면 403. 목록은 세션의 계정 ID로만 조회 |
| 패스키 삭제 | `revoke` | 본인 키인지 확인. 마지막 키 삭제 방지. 삭제와 전체 세션 종료, 추가 등록 대기 질문 무효화 |
| 일회 질문 | `remember`, `consume` | 서버 DB에 5분 보관. SQL UPDATE RETURNING으로 한 번만 소비. 실패한 검증의 질문도 소비 |
| 세션 | `session`, `lib/security.ts` | 임의 256비트 값의 해시만 서버 저장. 브라우저는 HttpOnly·SameSite=Strict 쿠키, 운영 환경에서 Secure 및 __Host 접두사. 절대 수명 12시간 |

패스키 추가·삭제에는 10분 이내의 로그인 세션이 필요하다. URL이나 본문의 `userId`로 소유자를 바꾸지 않는다. 미로그인 HTML/RSC 및 공개 클라이언트 번들에는 실제 메모 내용이 들어가지 않는다. 응답은 `Cache-Control: no-store`로 보낸다.

## ④ 안 열리는 것을 확인한 기록

자동 검증: `ENGINEERING_TEST_RESULT.md`, 요청·응답: `ENGINEERING_EVIDENCE.json`. 실제 HTTP, 로컬 D1, 실제 ECDSA 서명을 사용하는 합성 인증기로 검증했다. 쿠키·세션 값은 기록에서 `[REDACTED]`로 가렸다.

| 확인 | 성공 요청 | 거절 요청 |
| --- | --- | --- |
| 로그인 없이 열기 | 공개 `/` 200, 로그인한 `/api/private/notes` 200 | 미로그인 자료·패스키 목록 401 |
| 남의 패스키로 열기 | A는 A의 메모 3개, B는 B의 서로 다른 메모 3개 | A→B 개별 메모 및 B→A 개별 메모 모두 403. 거절 전후 자료 건수 3개 유지 |
| 이미 쓴 질문 재사용 | 올바른 서명의 첫 로그인 200 | 같은 서명·질문 재전송 400. 동시 두 요청도 200/400으로 하나만 통과 |
| 삭제 뒤 로그인 | 남은 패스키로 로그인 200, 메모 3개 유지 | 삭제한 패스키 로그인 401, 삭제 전 세션으로 조회 401 |

추가 확인: URL·본문에 B의 계정을 적어도 A 세션에서는 A 자료만 반환한다. 잘못된 서명·origin·userHandle은 401. 등록 취소 후 질문 재사용은 400이며 계정·키가 생성되지 않는다. 로그아웃 전 세션 재사용은 401. 마지막 키 삭제는 409. 등록·로그인 질문은 각각 두 요청의 값이 다르다.

**아직 실제 기기에서 통과로 표시할 수 없는 부분:** Windows PC·스마트폰의 등록·저장 위치·목록 화면, 실제 삭제 뒤 로그인 성공·실패. `DEVICE_CHECK_GUIDE.md`의 절차로 확인하고 실제 공개키·요청·응답·화면을 추가해야 한다.

## ⑤ AI와 나

- AI에게 맡긴 일: 구현, 자동 검증, 안내 카드 요구사항 정리, 문서 초안.
- 내가 직접 판단한 일: 기존 T01 소개를 이어가는 방향으로 시작했고 실제 확인 기기로 Windows PC와 스마트폰을 선택했다. 실제 패스키 등록·삭제는 직접 확인할 예정이다.
- AI 제안을 따르지 않은 일: 아직 사용자가 밝힌 사례가 없다. 완료 후 본인이 실제 선택에 맞춰 작성한다. AI가 대신 거절 사례를 만들지 않는다.

## ⑥ 아직 못 막은 것

- 사용 가능한 패스키를 모두 잃으면 기존 계정 복구를 제공하지 않는다. 마지막 키의 앱 내 삭제는 막지만 기기 분실·외부 관리자에서의 키 삭제까지 막지는 못한다. 새 계정을 만들어야 한다.
- 저장 위치는 사용자가 선택한 기록이며 앱이 실제 제공자 이름을 독립적으로 인증하지 않는다. 등록 창에서 선택한 제공자와 대조해야 한다.
- 기기 자체가 침해되거나 이미 열린 세션이 탈취된 경우까지 막지 못한다. 세션 만료와 키 삭제 시 세션 종료가 있지만 별도 관리자의 강제 잠금·고급 이상 징후 탐지는 없다.
- 기본적인 요청 횟수 제한은 있지만 대규모 분산 가입·자원 고갈에 대한 운영 수준의 방어는 제공하지 않는다. 실제 개인정보를 보관하는 서비스로 사용하지 않는다.
